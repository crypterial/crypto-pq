# 11. Stateful hash-based signatures

## 11.1 Model

1. A stateful private key exists only as a key object bound to a state store. It is created by
   `generateKeyPair` or `loadPrivateKey`; it has no `exportKey` and no import operation. Rationale:
   SP 800-208 §8.1 prohibits the export of private keying material; the state record ([11.7](#117-state-record-version-2)) is the
   only persistent form, and it is written only through the store contract.
2. The fixed behaviour of this section is the "critical or mandatory" case of P3: no option relaxes
   it.

## 11.2 Parameters

1. `parameters` is REQUIRED for `generateKeyPair`.
   - HSS/LMS: a list of 1 to 8 levels, top first, each a pair (LMS type name, LM-OTS type name) from
     [5.3](05-algorithms.md#53-stateful-hash-based-signatures). Every level MUST use the same hash function and output size as level 0 (SP 800-208 §4:
     different LMS and LM-OTS parameter sets can be used at different levels as long as all of them
     use the same hash function; RFC 8554 §6 alone does not impose this), and the sum of the heights
     MUST be at most 60.
   - XMSS and XMSS^MT: one parameter set name from [5.3](05-algorithms.md#53-stateful-hash-based-signatures), valid for the algorithm value (an XMSS^MT name
     given to `XMSS` is invalid, and the reverse).
2. An unknown name, an empty or too long level list, mixed hash functions or sizes, or a total height
   above 60 fails with INVALID_OPTION.
3. Rationale for the height limit: indices are 64-bit and the capacity 2^60 bounds every count [[D-38](decisions.md#decision-d-38)].

## 11.3 Levels, indices and trees

The following notation is used for the three algorithms.

1. Levels are numbered from 0 (top) to L − 1 (bottom). For HSS, level l is HSS level l with height
   h_l. For XMSS^MT with total height h and d layers, level l is the XMSS layer d − 1 − l and every
   level has height h′ = h/d (RFC 8391 §4.2). XMSS has one level, L = 1, h_0 = h.
2. H_l = h_l + h_(l+1) + … + h_(L−1), and H_L = 0. The capacity is N = 2^(H_0).
3. Every signature uses one index i, 0 ≤ i < N. At level l it uses tree number t_l(i) = i >> H_l and
   leaf q_l(i) = (i >> H_(l+1)) mod 2^(h_l) of that tree. Level 0 has the single tree 0.
4. The tree with number t at level l ≥ 1 (a child tree) is signed by tree t >> h_(l−1) of level l − 1,
   using its leaf t mod 2^(h_(l−1)) (the parent leaf).

## 11.4 Randomness [D-11]

All random values come from the entropy source ([14.3](14-security.md#143-entropy)), drawn when they are first needed:

| value | size | when | rule |
|---|---|---|---|
| HSS: I and SEED of the top LMS tree | 16 and m | key generation | SP 800-208 §6.1 |
| HSS: I and SEED of each child LMS tree | 16 and m | when the child tree is created | SP 800-208 §6.1: separate I and SEED per LMS instance |
| HSS: randomizer C of every LMS signature, including the signature of a child public key | n | per signature | SP 800-208 §6.1 |
| XMSS, XMSS^MT: S_XMSS, SK_PRF and SEED of the top tree | n each | key generation | SP 800-208 §6.2; §7.2.1 Algorithm 10′ |
| XMSS^MT: S_XMSS of each child tree | n | when the child tree is created | SP 800-208 §6.2: a separate S_XMSS per XMSS key pair; RFC 9802 §8 |

1. SEED (PUB_SEED) is shared by every tree of an XMSS^MT key (SP 800-208 §7.2).
2. One SK_PRF serves the whole XMSS^MT key; it is used only at the bottom level to derive r
   (SP 800-208 §7.2.1, Algorithm 12′). Rationale: SP 800-208 §7.2 states that a per-module SK_PRF
   "does not affect either interoperability or security"; crypto-pq is one module, so one SK_PRF
   generated by the approved source meets §6.2.
3. WOTS+ secret values are sk[j] = PRF_keygen(S_XMSS, SEED || ADRS) with the layer and tree addresses
   of their tree (SP 800-208 §7.2.1, Algorithm 10′). LM-OTS secret values follow RFC 8554 Appendix A
   with the I and SEED of their tree.
4. Signatures on child roots in XMSS^MT use r = 0 and M′ = root (SP 800-208 §7.2.1, Algorithm 12′,
   L > 0), which RFC 8391 §4.2.4 verification accepts.
5. The deterministic mode of [11.14](#1114-deterministic-mode-hazmat) replaces these draws with derivations, for test vectors only.

## 11.5 Signing

### 11.5.1 Current levels

A level l ≥ 1 is current for index i when its record ([11.7](#117-state-record-version-2)) has status signed, its tree number equals
t_l(i), and level l − 1 is current (level 0 is always current). If a level is not current, no level
below it is current.

### 11.5.2 Procedure

`sign(message)` on a key object whose next in-memory index is i MUST perform these steps in order:

1. If another `sign` or `exportTreeCache` on the same key object is running, fail with STATE_CONFLICT
   ([11.13](#1113-concurrency)).
2. If i = N: retry the erasure write of [11.12](#1112-exhaustion) item 2 if it is still pending (a failure of that retry
   is ignored), then fail with KEY_EXHAUSTED.
3. Let T be the set of levels l ≥ 1 that are not current for i. If T is not empty (a transition):
   1. Draw from the entropy source every random value that the new child trees and their signatures
      need ([11.4](#114-randomness-d-11)). On failure, fail with RNG_FAILURE; nothing has changed.
   2. Claim write: build a state record in which each level l in T has the record {tree t_l(i),
      status claimed}, `next` is max(next, i), and every other field is unchanged, and store it with
      `update(previous, new)`
      ([11.6](#116-state-store-contract)). On an error, fail with STATE_PERSIST_FAILED; on `false`, fail with STATE_CONFLICT. In
      both cases nothing was signed.
   3. For each level l in T, from the top down: build the child tree of number t = t_l(i) from its
      secrets; compute its public key (HSS: u32(lmsType_l) || u32(otsType_l) || I_l || root; XMSS^MT:
      root); sign it with the parent leaf ([11.3](#113-levels-indices-and-trees) item 4); verify that signature against the parent
      tree's public key. If a verification fails, apply step 3.5 and fail with SELF_TEST_FAILED.
   4. Signed write: build a state record in which each level l in T has the record {tree t, status
      signed, child secrets, root, parent signature}, and in which `next` is set to
      min(i + reserve, N) if i ≥ the stored `next`. Store it with `update`. On an error, apply step
      3.5 and fail with STATE_PERSIST_FAILED; on `false`, apply step 3.5 and fail with
      STATE_CONFLICT.
   5. Failure after the claim [[D-60](decisions.md#decision-d-60)]. When step 3.3 or 3.4 fails, the key object MUST wipe the new
      child secrets and signatures and set its in-memory index to min((t_m(i) + 1) << H_m, N), where
      m is the smallest level in T. It MUST NOT build or sign another tree under a parent leaf that
      the claim covered. This is the index that `loadPrivateKey` derives from the stored claim
      ([11.9](#119-loading) item 4), so a key object and a reload agree. If the new index is N, the erasure write of
      [11.12](#1112-exhaustion) item 2 becomes pending.
4. Otherwise, if i ≥ the `next` field of the stored record (index i is not reserved), store a record
   whose `next` is min(i + reserve, N) with `update` as in step 3.2.
5. Set the in-memory index to i + 1. Index i is now spent whatever happens next.
6. Compute the message signature with index i: HSS (RFC 8554 §6.2, Algorithm 8, with C drawn per
   [11.4](#114-randomness-d-11)); XMSS (RFC 8391 §4.1.9, Algorithm 12, with the key generation of SP 800-208 §7.2.1); XMSS^MT
   (SP 800-208 §7.2.1, Algorithm 12′ at the bottom level, assembled as RFC 8391 §4.2.4 with the stored
   child-root signatures).
7. Verify before release [[D-13](decisions.md#decision-d-13), [D-63](decisions.md#decision-d-63)]: verify every one-time signature computed during this call
   before it is released or stored: the message signature of step 6 and each child-root signature
   computed in step 3, each with the public key that signs it (RFC 8554 §6.3, Algorithm 6; RFC 8391
   §4.1.10, Algorithm 14). The stored child-root signatures copied from the state were verified when
   they were computed and again at load ([11.9](#119-loading) item 6); they MUST be copied byte for byte and need not
   be verified again. If a verification fails, wipe the signature and fail with SELF_TEST_FAILED.
8. Return the signature.

Rationale: the claim write makes the use of a parent leaf durable before the leaf signs anything.
Each root is therefore signed once (SP 800-208 §8.1 and its footnote 9), and a crash between the
claim and the signed write, or a failure there (step 3.5), leads to a skip ([11.9](#119-loading)), never to a second
signature by the same leaf. The
store holds every signature of a child root, so no root is signed again after a load. Step 4 makes the
index durable before the signature is released (SP 800-208 §8.1). Step 7 is a fault countermeasure:
a faulty signature, which can reveal one-time secret values, is never released. It does not detect a
fault that changes a child root before the root is signed; the sign-once rule of footnote 9 is what
makes such a fault harmless, because the faulty root is then the only root that the parent leaf
signs.

### 11.5.3 Key generation

`generateKeyPair({parameters, stateStore, reserve})` MUST perform these steps in order [[D-52](decisions.md#decision-d-52)]:

1. Check `parameters` ([11.2](#112-parameters)) and `reserve` ([11.11](#1111-reserve)); failures give INVALID_OPTION.
2. Draw the top secrets and, for each level l ≥ 1, the secrets of child tree 0 and the randomness of
   its parent signature ([11.4](#114-randomness-d-11)); failure gives RNG_FAILURE.
3. Build the top tree and compute the public key. For each level l ≥ 1, top first, build child tree 0,
   sign its public key with leaf 0 of the level above, and verify that signature (SELF_TEST_FAILED on
   failure, after wiping every secret).
4. Build the version 2 record with next = 0 and a signed record for tree 0 at every level, and store it
   with `update(absent, record)`. An error gives STATE_PERSIST_FAILED; `false` (the store already holds
   a state) gives STATE_CONFLICT. In both cases every secret is wiped and no key is returned.
5. Return the key pair; the private key's in-memory index is 0.

## 11.6 State store contract

1. The store has two operations ([6.4.8](06-api.md#648-state-store)). They are synchronous.
2. `read()` returns the bytes last stored, or absent if none were ever stored.
3. `update(previous, next)` MUST be an atomic compare-and-swap: if the stored value is byte-for-byte
   `previous` (absent: the store is empty), it replaces it with `next` and returns `true`; otherwise it
   changes nothing and returns `false`. A key object always passes as `previous` the exact record
   that it last read or stored with a successful `update`; a failed `update` does not change it.
4. `update` MUST make `next` durable (written to storage that survives a crash and a power loss) before
   it returns `true`.
5. `read` and `update` report failure in the language's way (exception, error value); the key maps it
   to STATE_PERSIST_FAILED.
6. The store MUST copy what it keeps. After `update` returns, the implementation MAY wipe both
   arguments, and after `read` returns, the implementation owns and MAY wipe the returned bytes.
7. The state record contains secrets. The store MUST protect it like a private key.
8. A state record MUST NOT be restored from a copy or backup, cloned, or used by two key objects or
   processes at once. Restoring an old record makes the key sign again with spent one-time keys and
   breaks the scheme (SP 800-208 §1.2 and §9.1; RFC 9802 §11). Compare-and-swap protects only against
   another writer on the same store; it cannot detect a rollback of the storage itself (for example a
   virtual machine or disk snapshot).
9. A store MUST NOT call back into the key object that is calling it; such a call fails with
   STATE_CONFLICT ([11.13](#1113-concurrency)).
10. The public documentation MUST state items 3, 4, 7 and 8.

## 11.7 State record, version 2

The state record is the byte string written to the store. Version 2 is written by crypto-pq 1.0
[[D-10](decisions.md#decision-d-10)]. All integers are big-endian.

| field | size | value |
|---|---|---|
| version | 1 | 0x02 |
| kind | 1 | 0x01 HSS/LMS, 0x02 XMSS, 0x03 XMSS^MT |
| parameters | HSS: 1 + 8L; XMSS, XMSS^MT: 4 | HSS: u8(L) then, for each level from the top, u32(LMS type code) \|\| u32(LM-OTS type code); XMSS, XMSS^MT: u32(OID) |
| flags | 1 | bit 0: derivation, 0 = entropy source ([11.4](#114-randomness-d-11)), 1 = deterministic ([11.14](#1114-deterministic-mode-hazmat)); bits 1-7 MUST be 0 |
| next | 8 | u64: the reserved bound; no index ≥ next has been used; 0 ≤ next ≤ N |
| top secrets | HSS: 16 + m; XMSS, XMSS^MT: 3n | HSS: I_0 \|\| SEED_0; XMSS, XMSS^MT: S_XMSS \|\| SK_PRF \|\| SEED |
| public key | HSS: 28 + m; XMSS, XMSS^MT: 4 + 2n | the raw public key ([10.1](10-key-formats.md#101-formats)) |
| records | variable | L − 1 level records for levels 1 to L − 1, top first (L = d for XMSS^MT); none for XMSS |
| checksum | 16 | the first 16 bytes of SHA-256 of every preceding byte |

A level record:

| field | size | value |
|---|---|---|
| tree | 8 | u64: the tree number t of the child tree at this level |
| status | 1 | 0x00 claimed: the parent leaf of tree t might have been used; 0x01 signed |
| child secrets | HSS: 16 + m; XMSS^MT: n | present only if signed. HSS: I_l \|\| SEED_l; XMSS^MT: S_XMSS of the tree |
| root | HSS: m; XMSS^MT: n | present only if signed: the root of tree t |
| parent signature | HSS: 12 + n(p + 1) + m·h of level l − 1's types; XMSS^MT: (len + h′)·n | present only if signed. HSS: the LMS signature of the child public key by the parent (RFC 8554 §5.4); XMSS^MT: the WOTS+ signature followed by the authentication path (RFC 8391 §4.2.3, one reduced XMSS signature) |

Notes:

- The checksum detects accidental damage. It is not a MAC: whoever can write the store can also roll it
  back, which no MAC prevents ([11.6](#116-state-store-contract) item 8). [[D-41](decisions.md#decision-d-41)]
- A record of level l is never smaller than the previous record of that level, so every state record
  of one key is later than the one it replaces.

`cross/treecache.txt` ([19.2](19-conformance.md#192-compliance-suite)): LMS_SHA256_M24_H5 with LMOTS_SHA256_N24_W4, generated by
`hazmat.generateStatefulKeyPair` at index 5. The bytes were computed from that key by the rules of
this section. The record has 128 bytes and no level records, because L = 1.

## 11.8 State record, version 1

Records written before crypto-pq 1.0 have version 0x01. crypto-pq 1.0 MUST NOT load them:
`loadPrivateKey` fails with INVALID_PRIVATE_KEY, as for any unknown version ([11.9](#119-loading) item 2) [[D-14](decisions.md#decision-d-14)]. It
MUST NOT convert, rewrite or delete such a record.

Rationale: version 1 derived the child trees from the top secrets and signed the child roots again
after every load, which SP 800-208 §6 and §8.1 (footnote 9) do not allow. A migration would sign each
current child root once more; a fault during that computation could produce a different root signed
by a one-time key that has already signed the original root in every released signature. Version 1
records were written only by pre-release versions.

## 11.9 Loading

`loadPrivateKey(stateStore, {reserve, treeCache})` MUST:

1. Check `reserve` ([11.11](#1111-reserve)) and read the store. A read error fails with STATE_PERSIST_FAILED; an absent
   value fails with INVALID_PRIVATE_KEY.
2. Check, in order, failing with INVALID_PRIVATE_KEY unless stated: the length is at least 18; the
   checksum; the version is 2 (version 1 and every other value fail, [11.8](#118-state-record-version-1)); the kind equals the
   algorithm value's kind (else ALGORITHM_MISMATCH).
3. Check, failing with INVALID_PRIVATE_KEY: the parameters are valid ([11.2](#112-parameters)) for the kind; the total
   length is exact for the parameters, flags and statuses; reserved flag bits are zero; every status
   is 0x00 or 0x01; next ≤ N; unless next = N, the public-key fields that the top secrets determine
   (HSS: L, the top types and I_0; XMSS and XMSS^MT: the OID and SEED) equal the stored public key,
   compared in constant time with only the result declassified. The stored root is checked when the
   top tree is built or restored ([11.10](#1110-tree-cache) item 4); a mismatch fails with INVALID_PRIVATE_KEY.
4. Set the in-memory index i = next. Then, for each level l from 1 to L − 1, top first:
   - if the record's tree is greater than t_l(i), fail with INVALID_PRIVATE_KEY;
   - if its status is claimed and its tree equals t_l(i), set i = (tree + 1) << H_l (skip the
     subtree whose parent leaf might have been used [[D-12](decisions.md#decision-d-12)]); if i > N, set i = N;
   - if its status is signed, its tree equals t_l(i), and level l − 1 is not current for i, fail with
     INVALID_PRIVATE_KEY.
5. If i = N, apply [11.12](#1112-exhaustion) item 2, ignore the tree cache, build no tree, and continue with item 7.
6. If `treeCache` is present, open it as in [11.10](#1110-tree-cache). Then build the tree t_l(i) of every level l that is
   current for i, from the cached nodes where the cache holds that tree. A child tree built from the
   secrets of its record MUST have the root that the record stores; a mismatch fails with
   INVALID_PRIVATE_KEY, as for the top root (item 3) [[D-73](decisions.md#decision-d-73)]; a cached tree follows [11.10](#1110-tree-cache) item 4. Then
   verify every signed record that is current for i (its parent signature against its parent); fail
   with SELF_TEST_FAILED if one does not verify.
7. Return the key object. The skip of item 4 is made durable by the next claim write.

`remainingSignatures()` returns N − i for the in-memory index i. Indices in [i, next) that were
reserved by a key object that no longer exists are lost on the next load; this is by design, as it
never reuses an index.

## 11.10 Tree cache

1. `exportTreeCache()` returns the public nodes of the trees that the key uses, so that a later
   `loadPrivateKey` can skip building them. It reveals no secret. The cache contains exactly one
   entry for each level l that is current for the in-memory index i ([11.5.1](#1151-current-levels)), top first, with tree
   number t_l(i); levels that are not current are omitted [[D-17](decisions.md#decision-d-17)]. The key holds these trees from
   `generateKeyPair` or `loadPrivateKey` onward ([11.9](#119-loading) item 6) and after every successful `sign`.
2. Format, version 1 (unchanged from the pre-1.0 format) [[D-17](decisions.md#decision-d-17)]:

   | field | size | value |
   |---|---|---|
   | version | 1 | 0x01 |
   | kind | 1 | as in [11.7](#117-state-record-version-2) |
   | parameters | as in [11.7](#117-state-record-version-2) | as in [11.7](#117-state-record-version-2) |
   | public key length | 4 | u32 |
   | public key | as stated | the raw public key |
   | tree count | 1 | number of trees that follow |
   | trees | variable | for each tree, top first: u8(position) \|\| u64(tree number) \|\| u8(low) \|\| u8(height) \|\| u8(node size) \|\| u32(node count) \|\| nodes |
   | tag | 32 | HMAC-SHA-256(K, every preceding byte) |

   - position: the HSS level (0 = top), or the XMSS layer (0 = bottom, d − 1 = top).
   - height: the tree's height; low = max(0, height − 15); node size: m or n; node count:
     2^(height − low + 1) − 1.
   - nodes: every node of heights low to height, height by height from low upward, left to right
     within a height, node-size bytes each.
   - K = HMAC-SHA-256(key = the ASCII string `crypto-pq tree cache v1`, data = the top secrets of
     [11.7](#117-state-record-version-2)), that is HKDF-Extract with the label as salt (RFC 5869 §2.2).

   Example: the tree cache that the key of the example in [11.7](#117-state-record-version-2) exports, from the record "one level before
   signing" of `cross/treecache.txt` ([19.2](19-conformance.md#192-compliance-suite)). It has 1628 bytes; 61 of the 63 nodes are left out below.

   ```
   01                                     version
   01                                     kind: HSS/LMS
   01 0000000a 00000007                   parameters, as in 11.7
   00000034                               public key length: 52
   000000010000000a0000000748c1cc4d
   8bba1e3cafbbf4d4829d7ad0ef575242
   7fd98b2b649423d033aadf199e66b507
   fb160b86                               public key
   01                                     tree count
   00 0000000000000000 00 05 18 0000003f  position 0, tree 0, low 0, height 5, node size 24, 63 nodes
   4e39f0a279ec28309d6af8c1f7d64f9f
   d9d51059a50a35d0                       first node: height 0, leaf 0
   ...                                    61 nodes
   ef5752427fd98b2b649423d033aadf19
   9e66b507fb160b86                       last node: the root, equal to the root in the public key
   70a14714f7a368afec4a67d3c7a60345
   bfe205903a16b90bb1759259dcbf9a83       tag
   ```
3. Opening a cache at load MUST check, in this order: the structure and lengths (INVALID_ENCODING); the
   version (INVALID_ENCODING); the kind (ALGORITHM_MISMATCH); the parameters equal the state's, and
   the public key fields that the top secrets determine equal them (INVALID_ENCODING); the tag, in
   constant time (INVALID_ENCODING); for each tree, that the trees appear in strictly top-first order
   (HSS levels increasing, XMSS layers decreasing) and that low, height, node size and node count
   match the parameters (INVALID_ENCODING). A kind byte other than 0x01 to 0x03 makes the structure
   unreadable and fails with INVALID_ENCODING; a known kind of another algorithm value fails with
   ALGORITHM_MISMATCH.
4. A cached tree whose tree number is not t_l(i) at its level l, for the index i that the load
   computed ([11.9](#119-loading) item 4), is stale: it is ignored and the tree is built from the secrets [[D-64](decisions.md#decision-d-64)]. A
   cache entry that is malformed, repeats the position of an earlier entry, breaks the top-first
   order, or has a position that is not a level of the key fails with INVALID_ENCODING (item 3).
   For every other tree, the root recomputed from its nodes MUST equal the public key's root (top
   tree) or the root of the current level record (child trees); otherwise INVALID_ENCODING.
5. Restoring an old tree cache is harmless: it holds public data and stale trees are skipped.
6. `exportTreeCache` on a key that is signing fails with STATE_CONFLICT. On an exhausted key
   (in-memory index N) it fails with KEY_EXHAUSTED: its secrets are erased ([11.12](#1112-exhaustion)), so no tag can be
   computed, and no tree remains in use [[D-39](decisions.md#decision-d-39)].

## 11.11 Reserve

1. `reserve` is the number of indices that one store write claims. It is an integer of 1 to 2^64 − 1;
   the default is 1. A value of 0 fails with INVALID_OPTION (in Go, see 24.1).
2. `reserve` is not stored in the state record; each key object takes it as an option.
3. Larger reserves reduce store writes and lose up to reserve − 1 indices when a key object is dropped.

## 11.12 Exhaustion

1. When the in-memory index equals N, `sign` and `exportTreeCache` fail with KEY_EXHAUSTED and
   `remainingSignatures()` returns 0 [[D-39](decisions.md#decision-d-39)]. The public key still verifies every earlier signature.
2. Erasure on exhaustion [[D-54](decisions.md#decision-d-54)]: when a `sign` leaves the in-memory index equal to N, the
   implementation MUST, after step 7 of [11.5.2](#1152-procedure) and before returning the signature, store a final record
   in which next = N and the top secrets and every child-secrets field are replaced by zero bytes of
   the same length, and MUST wipe every secret in memory. A failure of that write does not fail the
   `sign`; the next `sign` or load retries it (and `sign` then fails with KEY_EXHAUSTED). A load that
   finds next = N with non-zero secrets also stores the final record. The kind, parameters, flags,
   public key, records and lengths are kept, so the final record still loads and reports exhaustion.
   Rationale: an exhausted key has no legitimate use for its secrets, and erasing them removes the
   risk of reuse after a rollback of the store.

## 11.13 Concurrency

1. A stateful private key object serializes nothing and never waits. A second `sign` or
   `exportTreeCache` that starts while a `sign` on the same object is running fails at once with
   STATE_CONFLICT, including a call made from inside the store's `update` or `read`.
2. In Rust, `sign` takes exclusive access (`&mut self`), so the overlap cannot be expressed; the rule
   holds trivially.
3. Two key objects loaded from the same store detect each other only through compare-and-swap: the
   later writer fails with STATE_CONFLICT.

## 11.14 Deterministic mode (hazmat)

`hazmat.generateStatefulKeyPair` (Section [13](13-hazmat.md)) creates keys with flags bit 0 set. Such keys are for test
vectors and interoperability tests only and do not conform to SP 800-208 §6 [[D-15](decisions.md#decision-d-15)]. In this mode:

1. The top secrets are the caller's seed (HSS: I_0 || SEED_0, 16 + m bytes; XMSS, XMSS^MT:
   S_XMSS || SK_PRF || SEED, 3n bytes); another length fails with INVALID_LENGTH.
2. HSS: for a parent tree with identifier I and seed SEED, the child under leaf q has
   I_child = H(I || u32(q) || u16(0xFFFF) || 0xFF || SEED) truncated to 16 bytes and
   SEED_child = H(I || u32(q) || u16(0xFFFE) || 0xFF || SEED) truncated to m bytes; every LMS
   signature at leaf q uses C = H(I || u32(q) || u16(0xFFFD) || 0xFF || SEED) truncated to n bytes.
   H is SHA-256 for the SHA-256 families and SHAKE256 for the SHAKE families. This is the convention
   of the reference implementation used by the test cases of RFC 8554 Appendix F and RFC 9858 (the
   values 0xFFFD to 0xFFFF lie outside the chain indices of RFC 8554 Appendix A).
3. XMSS^MT: every tree uses the top S_XMSS, with its own layer and tree addresses (the key generation
   of RFC 8391 §4.2.2).
4. The start index is a parameter; it MUST satisfy index < N, else INVALID_OPTION [[D-68](decisions.md#decision-d-68)].
5. Every other rule of this section, including the claim and signed writes and verification before
   release, applies unchanged.

## 11.15 Statement of conformance to SP 800-208

1. crypto-pq implements the parameter sets of SP 800-208 §4 and §5, the modified XMSS^MT algorithms of
   §7.2.1, and the signing requirements of §8.1: the index is stored in non-volatile storage before a
   signature is released, and no one-time key signs twice. Every value that §6 requires from an
   approved random bit generator is drawn fresh from the operating-system entropy source ([14.3](14-security.md#143-entropy));
   whether that source is an approved RBG in the sense of SP 800-90 depends on the operating system
   and its configuration, not on crypto-pq.
2. SP 800-208 §8.1 also requires a hardware cryptographic module validated at FIPS 140 level 3, an
   entropy source inside the module boundary, and no export of private keying material. A software
   library cannot meet these requirements: the state store is outside the library [[D-16](decisions.md#decision-d-16)].
3. Text published by the project MUST NOT claim SP 800-208 validation or FIPS 140 validation. It MAY
   state that crypto-pq implements the SP 800-208 algorithms and the requirements of item 1.
