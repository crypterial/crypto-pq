# 18. Testing and continuous integration

## 18.1 Checks per language

The CI of every implementation MUST run, for every backend:

1. the language's standard formatter in check mode, where the language has one;
2. the compiler, linter or static type checker with warnings treated as errors, for every build
   configuration and cross target;
3. a check that every generated file (assembly, embedded WebAssembly modules, generated source) equals
   the output of its generator;
4. the tests, on the minimum supported and the current toolchain or runtime, and in every build mode
   that the profile names;
5. the tests with CPU-specific code disabled, through the switch that the profile names ([15.3](15-platforms.md#153-cpu-specific-code) item 6);
6. the constant-time check of [14.1](14-security.md#141-constant-time) item 7;
7. for the core, the stack bound test of [14.6](14-security.md#146-memory) item 3.

## 18.2 CPU tiers

CI MUST run the tests on processor models, emulated where necessary, that together select every
CPU-specific tier of [15.3](15-platforms.md#153-cpu-specific-code) and the portable code, and on native x86-64 and ARM64 hardware. A test
counts the kernels each model selects and fails if the count differs from the expected one.

## 18.3 Platforms

CI MUST build and test: Linux x86-64 and ARM64, macOS ARM64 (and x86-64 where a package ships for it),
Windows x86-64 and ARM64; RISC-V 64, 32-bit x86 (Go) and big-endian s390x under emulation; Linux musl;
every runtime of [15.2](15-platforms.md#152-supported-platforms).

## 18.4 Vectors and robustness

1. The compliance suite ([19.2](19-conformance.md#192-compliance-suite)) runs on every push in every language and backend, and its files MUST be
   unmodified, as checked against `SHA256SUMS`.
2. The cross-language files MUST be regenerated by the reference generator and compared in CI.
3. Fuzz targets for every parser and every public operation run weekly (Go native fuzzing; long
   robustness runs in the other languages).
4. Large-data tests (inputs of 1 to 8 GiB for SHA-2, SHA-3 and SHAKE; BLAKE2 above 4 GiB) run weekly.
5. Differential tests compare the TypeScript WebAssembly and JavaScript backends and the Python native
   and pure backends on random inputs.

## 18.5 Supply chain

1. Every CI dependency (actions, container images, test tools) is pinned by commit hash, digest or
   version.
2. CI runs only the CI platform's own actions and an allow-listed set of toolchain actions.
3. Builds of the core and of every package are reproducible: two builds on different host
   architectures produce identical bytes.
