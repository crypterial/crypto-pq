# Appendix B. Principle conformance review

| principle | how this document applies it | tensions |
|---|---|---|
| P1 zero third-party code | No runtime dependency in any package ([17](17-implementation-conventions.md) item 1, [23.4](profiles/rust.md#234-build-packaging-and-platforms), 24.4, 25.4, 26.4, 27.4); the pure Python backend uses no cryptographic standard-library module (27.2); Zig's own wipe instead of the standard library's (25.2). | Go uses `crypto/rand` and Python `os.urandom` for entropy: inside the boundary of P1 (operating-system access). Under `GODEBUG=fips140`, Go's `crypto/rand` passes through the runtime's DRBG, a choice of the program that the documentation states ([D-59](decisions.md#decision-d-59)). Test-only tools (valgrind, emulators, mypy, the TypeScript compiler) never ship. |
| P2 standardized or proven | Every algorithm of Section [5](05-algorithms.md) cites a final standard; drafts are excluded ([4.2](04-scope.md#42-excluded)). | FrodoKEM rests on an ISO standard whose text is not public; the algorithm text used is an Internet-Draft that cites it. BLAKE3 and BLAKE2 are not NIST standards; they are included as production-proven by major vendors and are not accepted as pre-hash. |
| P3 options with safe defaults | Hedged signing, self-tests, pure mode, full-length MAC tags (HMAC, KMAC and BLAKE2-MAC `length`, [D-33](decisions.md#decision-d-33)), `reserve` 1, automatic backend selection are defaults; alternatives are options. | Fixed by necessity: the pre-hash strength policy, the stateful rules (Section [11](11-stateful-signatures.md)), the import consistency tests, verification before release. Each is a security-critical case that P3 allows. |
| P4 same keywords | Section [16](16-naming.md) maps every name; [D-19](decisions.md#decision-d-19), [D-20](decisions.md#decision-d-20), [D-24](decisions.md#decision-d-24), [D-25](decisions.md#decision-d-25), [D-55](decisions.md#decision-d-55), [D-56](decisions.md#decision-d-56) make the names identical. | Go's zero-value idiom ([D-18](decisions.md#decision-d-18)) and `SelfTest` type ([D-19](decisions.md#decision-d-19)); the `_into` forms exist only in Rust and Go; Zig's `deinit`. These are idiom, not different words. |
| P5 five languages | Part II has one profile per language. | The Python native backend and the TypeScript WebAssembly backend run the Zig core: their native code is not independent of Zig. Their pure backends are independent implementations. |
| P6 thoroughness | The review checks every algorithm below. | |
| P7 never asynchronous | [15.1](15-platforms.md#151-synchronous-operation); synchronous stores; synchronous WebAssembly compilation. | Browsers can restrict synchronous compilation of large modules on the main thread ([15.1](15-platforms.md#151-synchronous-operation)); the operating system can block entropy at boot ([14.3](14-security.md#143-entropy)). |
| P8 no heap bloat | [14.6](14-security.md#146-memory); caller buffers (`_into`); FrodoKEM never caches A. | State record version 2 grows with the levels (up to tens of kilobytes for 8-level HSS with W = 1); stateful keys hold tree nodes (up to about 2 MiB per held tree of height 20 with n = 32). Both are inherent to SP 800-208 conformance and fast loading; the tree cache need not be used. |
| P9 universal | [15.2](15-platforms.md#152-supported-platforms) to [15.3](15-platforms.md#153-cpu-specific-code); portable twins; CPU models in CI ([18.2](18-testing.md#182-cpu-tiers)); 32-bit and big-endian ([18.3](18-testing.md#183-platforms)). | No AVX-512 or RISC-V kernels in 1.0 ([D-44](decisions.md#decision-d-44)): the portable code runs on every platform, and CPU-specific code exists only for x86-64 and ARM64. |
| P10 data-independent timing | [14.2](14-security.md#142-data-independent-timing-dit) exactly as decided; [D-45](decisions.md#decision-d-45) for hashes. | DIT cannot be set in WebAssembly, JavaScript or pure Python; Windows ARM64 reports none. |
| P11 security first | Import consistency tests ([D-06](decisions.md#decision-d-06), [D-47](decisions.md#decision-d-47), [D-61](decisions.md#decision-d-61)), verification before release ([D-13](decisions.md#decision-d-13)), skip instead of re-sign after a crash or a failure ([D-12](decisions.md#decision-d-12), [D-60](decisions.md#decision-d-60)), refusal of version 1 records ([D-14](decisions.md#decision-d-14)), no silent fallback from a failing native module ([D-27](decisions.md#decision-d-27)), erasure on exhaustion ([D-54](decisions.md#decision-d-54)), no panics ([D-03](decisions.md#decision-d-03)). | The pure backends cannot guarantee constant time or wiping ([14.1](14-security.md#141-constant-time) item 8); garbage-collected languages cannot guarantee wiping ([14.5](14-security.md#145-wiping) item 3). Stated, with the native backends as defaults. |
| P12 post-quantum only | X-Wing and X25519 excluded ([4.2](04-scope.md#42-excluded)); every asymmetric algorithm is lattice- or hash-based. | Small-output symmetric functions (SHA-224, SHA-512/224, SHA3-224, BLAKE2b-160, BLAKE2s-128, BLAKE2s-160, BLAKE2s-224, and MAC tags shortened with `length`) are below the quantum-resistant collision sizes: kept for interoperability; never a default; never a pre-hash. |
| P13 production first | [15.4](15-platforms.md#154-performance): performance is not part of conformance; Rust first ([22](22-profile-rules.md) item 3). | |
| P14 wording | [15.4](15-platforms.md#154-performance) item 2, [20.4](20-versioning.md#204-release-process) item 7. | |
