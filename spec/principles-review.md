# Appendix B. Principle conformance review

| principle | how this document applies it | tensions |
|---|---|---|
| P1 zero third-party code | No runtime dependency and no dev-dependency ([17](17-implementation-conventions.md) item 1, [23.4](profiles/rust.md#234-build-packaging-and-platforms) item 2); the crate is `no_std` and calls the operating-system entropy interfaces itself ([14.3](14-security.md#143-entropy), [23.2](profiles/rust.md#232-security-mechanics) item 5). | The entropy interfaces are operating-system access, inside the boundary of P1. Test-only tools (valgrind, emulators) never ship. |
| P2 standardized or proven | Every algorithm of Section [5](05-algorithms.md) cites a final standard; drafts are excluded ([4.2](04-scope.md#42-excluded)). | FrodoKEM rests on an ISO standard whose text is not public; the algorithm text used is an Internet-Draft that cites it. BLAKE3 and BLAKE2 are not NIST standards; they are included as production-proven by major vendors and are not accepted as pre-hash. |
| P3 options with safe defaults | Hedged signing, self-tests, pure mode, full-length MAC tags (HMAC, KMAC and BLAKE2-MAC `length`, [D-33](decisions.md#decision-d-33)), `reserve` 1 are defaults; alternatives are options. | Fixed by necessity: the pre-hash strength policy, the stateful rules (Section [11](11-stateful-signatures.md)), the import consistency tests, verification before release. Each is a security-critical case that P3 allows. |
| P4 same keywords | Section [16](16-naming.md) maps every keyword to its Rust form; [D-24](decisions.md#decision-d-24) and [D-25](decisions.md#decision-d-25) fix the names that needed a decision. | The `_into` forms and `Drop` are items that Rust idiom adds ([16.1](16-naming.md#161-keywords)), not different words. |
| P5 language-neutral specification | Part I states the behaviour without reference to a programming language; the compliance suite ([19.2](19-conformance.md#192-compliance-suite)) tests it with plain-text files; Part II holds the Rust profile ([22](22-profile-rules.md) item 3). | A few rules of Part I name their Rust form directly: the constant-time method ([14.1](14-security.md#141-constant-time) item 7), the manifests ([20.1](20-versioning.md#201-versions) item 2) and the release tag ([20.4](20-versioning.md#204-release-process) item 1). The `cross/` files are written by a generator in the Rust test suite ([18.4](18-testing.md#184-vectors-and-robustness) item 2). |
| P6 thoroughness | The review checks every algorithm below. | |
| P7 never asynchronous | [15.1](15-platforms.md#151-synchronous-operation); synchronous stores. | The operating system can block entropy at boot ([14.3](14-security.md#143-entropy) item 4). |
| P8 no heap bloat | [14.6](14-security.md#146-memory); caller buffers (`_into`); FrodoKEM never caches A. | State record version 2 grows with the levels (up to tens of kilobytes for 8-level HSS with W = 1); stateful keys hold tree nodes (up to about 2 MiB per held tree of height 20 with n = 32). Both follow from SP 800-208 conformance and from signing and loading without rebuilding the trees; the tree cache is optional. |
| P9 universal | [15.2](15-platforms.md#152-supported-platforms) to [15.3](15-platforms.md#153-cpu-specific-code); portable twins; CPU models in CI ([18.2](18-testing.md#182-cpu-tiers)); 32-bit and big-endian ([18.3](18-testing.md#183-platforms)). | No AVX-512 or RISC-V kernels in 1.0 ([D-44](decisions.md#decision-d-44)): the portable code runs on every platform, and CPU-specific code exists only for x86-64 and ARM64. |
| P10 data-independent timing | [14.2](14-security.md#142-data-independent-timing-dit) exactly as decided; [D-45](decisions.md#decision-d-45) for hashes. | DIT exists only on ARM64 processors with FEAT_DIT; Windows ARM64 reports none ([14.2](14-security.md#142-data-independent-timing-dit) item 3). |
| P11 security first | Import consistency tests ([D-06](decisions.md#decision-d-06), [D-47](decisions.md#decision-d-47), [D-61](decisions.md#decision-d-61)), verification before release ([D-13](decisions.md#decision-d-13)), skip instead of re-sign after a crash or a failure ([D-12](decisions.md#decision-d-12), [D-60](decisions.md#decision-d-60)), refusal of version 1 records ([D-14](decisions.md#decision-d-14)), erasure on exhaustion ([D-54](decisions.md#decision-d-54)), no panics ([D-03](decisions.md#decision-d-03)). | Copies that the compiler makes in registers or spill slots cannot be wiped ([14.5](14-security.md#145-wiping) item 3, [23.2](profiles/rust.md#232-security-mechanics) item 3). Stated in the documentation. |
| P12 post-quantum only | X-Wing and X25519 excluded ([4.2](04-scope.md#42-excluded)); every asymmetric algorithm is lattice- or hash-based. | Small-output symmetric functions (SHA-224, SHA-512/224, SHA3-224, BLAKE2b-160, BLAKE2s-128, BLAKE2s-160, BLAKE2s-224, and MAC tags shortened with `length`) are below the quantum-resistant collision sizes: kept for interoperability; never a default; never a pre-hash. |
| P13 production first | [15.4](15-platforms.md#154-performance): performance is not part of conformance; the release gate ([19.5](19-conformance.md#195-release-gate)) requires conformance, the security checks and reproducible artifacts. | |
| P14 wording | [15.4](15-platforms.md#154-performance) item 2, [20.4](20-versioning.md#204-release-process) item 7. | |
