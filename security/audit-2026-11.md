# Source audit, November 2026

This is the record of the audit of the crypto-pq source in November 2026 and of the fixes that
followed it. The decisions D-115 to D-119 of [`spec/decisions.md`](../spec/decisions.md) and the
pull requests named below hold the measurements in full; this record says what was examined, what
was found, how each finding was fixed and what was not covered.

## Nature of the audit

The audit is AI-assisted. It was run by the maintainer with the model Claude Mythos 5.2
(`claude-mythos-5-2`) in Claude Code. It is not a third-party audit, and no human auditor outside
the project took part.

- First pass: 2026-11-16, at the reasoning effort `xhigh`, paused the same day.
- Full audit: 2026-11-18, at the maximum reasoning effort, in one session without sub-agents.
- Fixes and further searches: 2026-11-18 and 2026-11-19. On 2026-11-19 the wider searches and the
  code of D-118 were run by AI agents of the same model at medium effort, and the auditing session
  read their whole diff before the merge.
- 2026-11-20: the auditing session measured the tree of D-118 anew, which led to D-119. The code
  of D-119 and the measurement of the release 1.0.1 were run by AI agents of a Claude Opus model
  at medium effort; the auditing session read the diff of D-119 whole before the merge and the
  outputs of the measurement.

The commit audited is c48e64f on `main`, which implements the draft of specification 2.0 and
carries the crate version 1.0.1. Every fix named below is on `main` at 456cf5c.

## Scope and reading

The whole Rust source was read: every line of `rust/src`, the test modules included, of
`rust/tests` and of `tools/`, with `rust/build.rs` and `rust/Cargo.toml`. The first report, on
2026-11-18, rested on about 61 percent of the non-test source; the auditing session corrected its
statement of coverage to the maintainer the same day, and the reading of the rest (the kernel
bodies under `rust/src/cpu`, the test code and the tools) was finished on 2026-11-18. Of the CI
workflows, `release-rust.yml`, `fuzz.yml` and the jobs of `ci.yml` that the checks used were read.
Not read line by line: the data under `vectors/` and most of the prose of `spec/`.

The reading covered memory safety (every `unsafe` block, the 61 inline assembly blocks against
their operand options, the 8 `assume_init` sites, the pointer wrappers of the CPU modules),
constant time (branches, indices and the 75 declassification sites), the CPU feature detection and
the guard of every kernel call, the parameters and steps of each algorithm against FIPS 203, 204
and 205, RFC 8554, 8391, 9858, 2104, 5869 and 7693 and NIST SP 800-208 and 800-185, the encodings,
the stateful key model, and the wipes of secret values.

## Methods

- **Source review**, in an order set by risk, of every file named above.
- **Search of the dead stack.** A harness paints the stack below the caller, runs one operation and
  searches the painted region for the secret values of that operation: keys, seeds, randomness,
  shared secrets, keyed states, and for BLAKE2 and BLAKE3 every state word of every keyed
  compression. It derives the values itself and checks the derivation against the library's
  outputs (for example the HMAC tag, the FORS values against the signature, the secret vectors of
  ML-KEM and ML-DSA against the public key).
- **Depth probes.** A build reads, at each place that writes zeros over the stack, the lowest byte
  that was written under it and the lowest byte that is not zero. The sizes of the zeros of D-115
  to D-118 come from these depths.
- **Emulated processor models.** x86-64 builds ran under `qemu-x86_64` as EPYC-Milan, Haswell and
  Nehalem, and from 2026-11-19 also as the first EPYC, EPYC-Milan with family 1Ah, Haswell with
  model 8Fh and qemu64, each chosen for the kernels that it makes the library select. ARM64
  builds ran as Cortex-A72 and Neoverse N1, which have neither the SHA-3 nor the SHA-512
  instructions.
- **Native runs on ARM64**, on an Apple M3 under Linux in a virtual machine, and **on x86-64 under
  Windows**, on one AMD Zen 3 processor, for the target `x86_64-pc-windows-gnu`.
- **Builds.** The release build at opt-levels 3, 2, s, z, 1 and 0, the test profile (opt-level 3
  with debug assertions), fat LTO, one codegen unit, the portable build (`--cfg
  crypto_pq_portable`), the build for x86-64-v3 and, from 2026-11-19, x86-64-v3 with one codegen
  unit and with fat LTO; Rust 1.99.0, and 1.89 for the minimum version.
- **Machine code.** Normalized disassembly of the release library, compared function by function
  before and after each fix.
- **CI.** The test `rust/tests/stack.rs`, written during the audit, runs in CI on the hosted
  runners, among them processors with AVX-512VL.

On the maintainer's machine the library was built and run in a container without network
access, with the sources mounted read-only.

Since D-119 the zeros after a keyed hash or a KDF are written in every build at the opt-levels 1,
2, s and z, and at opt-level 3 only with the Cargo feature `stack-zeros`: at opt-level 3 the
keyed-hash parts of the fixes of F4 and N1 and the zeros of D-117 depend on the feature. See
[After a keyed hash](#after-a-keyed-hash).

**F1.** `drop(lanes)` moved the lanes of the F chains (5,184 bytes on ARM64) by value; the drop
wiped the copy and the original stayed on the stack. After a signature it held the secret values
of the last sixteen leaves of the last FORS tree, with every parameter set on x86-64 and with the
SHA-2 sets on ARM64, and with SLH-DSA-SHAKE-128f and SLH-DSA-SHAKE-192f on ARM64 and in builds
without the CPU kernels it held SK.seed, after key generation too. It broke
[14.5](../spec/14-security.md#145-wiping) item 1 and D-76. Both calls were removed, so the lanes
are wiped where they are. rust-v1.0.0 and rust-v1.0.1 do not have the flaw.

**F2.** At opt-level 2 on x86-64 with the SHA extensions, a copy of both SHA-256 streams was a call
to memcpy, around which the registers with the key blocks were saved on the stack: HMAC-SHA-256
left the key XORed with its pads, and HKDF-SHA-256 its PRK the same way. Below opt-level 3 the
feed-forward now keeps the two state vectors of each stream alone; at opt-level 3 the code is
unchanged.

**C3.** The portable BLAKE3 compression had no wipe of its state and message words: at opt-levels
s and z an ARM64 core on the portable code left the state after the rounds of a keyed hash of at
most 64 bytes. These are wiped below opt-level 3 now.

**SLH-DSA frames (no identifier).** The first CI run of #88 found, in the test profile on a Xeon
Platinum 8573C with AVX-512VL, the last FORS secret value of SLH-DSA-SHAKE-256f and -256s in the
frame of a hash kernel. A signature with SLH-DSA-SHA2-128f or -128s at opt-levels 1, s and z on
x86-64, and with the SHA-2 sets of 192 and 256 bits with fat LTO on ARM64, left the outer HMAC
state of PRF_msg under SK.prf. No wipe of a named buffer reaches a value
that the compiler saved from a register. Decision D-115: key generation, the import of a private
key and signing end by writing zeros over the stack under them, 16 KiB at opt-level 3, 24 KiB at
1, 2, s and z and 48 KiB at 0.

**F3.** Below opt-level 3, kernels of HMAC and HKDF passed arrays of key words by value, which the
named wipes did not reach: on ARM64 at opt-levels s and z HMAC left the key XORed with its pads
and its key states, and HKDF its PRK and output; on x86-64 SLH-DSA-SHA2-128f left SK.prf through
PRF_msg. The SLH-DSA part is covered by the zeros of D-115. D-116 gave a MAC and a KDF in one call
16 KiB of zeros at opt-levels 1, 2, s and z, and D-117 gave the key setup and the end of an
incremental MAC the same there. D-118 put these zeros behind `stack-zeros` too, and D-119 writes
them in every build again; see [Decisions D-118 and D-119](#decisions-d-118-and-d-119).

**F4 and F9.** D-76 had left register arrays unwiped at opt-level 3, on the ground that the
compiler keeps them in registers; machine code showed the one-state Keccak rounds on x86-64
writing 28 stack slots that nothing wiped. What stays depends on the build: FrodoKEM left its whole
shared secret after encapsulation and decapsulation in every x86-64 build measured, in the portable
build on ARM64 and with FrodoKEM-1344 as Cortex-A72 and Neoverse N1 (F9), ML-KEM its
shared secret and coins when built for x86-64-v3 and sigma and the coins with fat LTO on ARM64,
ML-DSA rho', K and the states of H(xi) after key generation in the portable builds, and KMAC256
part of its states. Decision D-116: the operations of ML-KEM, ML-DSA and FrodoKEM on secret values
end with zeros over the stack under them at every opt-level. KMAC is covered by D-117.

**F5 to F8.** Found by reading, not measured: below opt-level 3, arrays of secret vectors in the
FrodoKEM product kernels (F5), the ARM64 noise sampler (F6) and the x86-64 ML-KEM kernels (F7),
and the key words of BLAKE3's one-block kernels and by-value helper arrays of the BLAKE3, SHA-2 and
HMAC kernels (F8), are copied in forms that the named wipes do not reach. The named wipes of these
arrays were not added; the zeros over the stack cover them instead. The frames of F5 to F7 lie
under the zeros of D-116. F8 lies under the zeros of a MAC or a KDF, which D-118 had made
optional at every opt-level; that F8 and the keyed part of F3 then rested on an option is what
led to the measurement of 2026-11-20 and to D-119, which writes these zeros below opt-level 3 in
every build.

**Keyed hashes at opt-level 3 (no identifier).** On 2026-11-18 the search, widened to every state
word of the keyed compressions, found in fourteen builds at opt-level 3, without zeros: after a
BLAKE2b MAC the chaining value after the key block, and after an empty message the key; after a
BLAKE2s MAC of an empty message 8 to 20 bytes of the key; after HMAC-SHA-512 the state after the
outer key block; after HKDF-SHA-512 its output with fat LTO on ARM64; after KMAC256 up to 120
bytes of its final state; after BLAKE3-KDF 12 bytes of the input keying material on ARM64; after a
keyed BLAKE3 of 16 KiB 12 to 20 bytes of the key on ARM64; and, with debug assertions on x86-64,
the whole key after a keyed BLAKE3 of 16 KiB and a whole compression state after one of at most a
chunk. Decision D-117 gave a MAC and a KDF in one call zeros at opt-level 3 too.

**N1.** An incremental MAC (`MacAlgorithm::create` or `key`, then `update` and `digest`) left its
keyed state in frames of the library at every opt-level: the HMAC states after the key blocks, the
KMAC state after the key and the BLAKE2 key. D-117 ends the key setup and the end of an
incremental MAC with zeros; since D-119 these are written in every build below opt-level 3 and
with `stack-zeros` at opt-level 3. A `Mac` and a `MacKey` are returned by value, and the copy
that the compiler keeps in the caller's own frame cannot be reached by the library; the API
documentation, both READMEs and the Rust profile state it.

**C1.** The READMEs and the crate documentation said that the asymmetric operations run with DIT
on ARM64 CPUs with FEAT_DIT. That holds under Linux and Android, which report the feature, and
under macOS, whose target has it; iOS, Windows and the BSDs run without it, as
[14.2](../spec/14-security.md#142-data-independent-timing-dit) item 4 says. The documents now name
the systems.

## Decisions D-118 and D-119

A size of zeros is the deepest that the calls went in the builds, on the processors and for the
lengths that were run, with a margin. On 2026-11-19 a wider search, with later calls in one
process, more processor models, dense grids of lengths and the combined builds, found four cases
on the tree of D-117 that went deeper than its zeros:

1. A keyed BLAKE3 in one call on Intel cores from Golden Cove on without AVX-512, which run the
   code before the row kernels, in a call that is not the first of its process: 407 bytes deep
   against 320 bytes of zeros for at most a block, and with debug assertions the search found a
   pair of words of the state of a keyed compression.
2. BLAKE3-KDF with fat LTO: a later derivation of at most 64 bytes went 2,095 bytes deep against
   1,984, and the search found 8 bytes of the input keying material.
3. HMAC in one call under a key longer than a block or with a tag shorter than the digest, with
   fat LTO or in one codegen unit: with SHA-384 or SHA-512 the search found the whole state after
   the outer key block, 64 bytes, in one codegen unit on x86-64 and, with fat LTO and in one unit,
   on ARM64 cores without the SHA-512 instructions, and 16 to 32 of its bytes with fat LTO on
   x86-64.
4. The key setup of an incremental MAC in a build for x86-64-v3 in one codegen unit: with KMAC256
   the search found the state after the key, 200 bytes.

Decision D-118 made the zeros of D-116 and D-117 after a keyed hash or a KDF an option, the Cargo
feature `stack-zeros`, which is not a default feature, at every opt-level. Its reason: the
standards of these functions ask for the destruction of keys and intermediate values, which the
wipes of the named buffers do; the zeros go beyond that, cost every call, and hold only for the
builds that were measured. With the feature the sizes at opt-level 3 are measured anew over the
cases above: HMAC takes its size by the lengths of its key and tag, and a keyed BLAKE3 on x86-64
by the path that ran. The zeros of ML-KEM, ML-DSA, FrodoKEM and SLH-DSA are not part of the
option: they are always written.

On 2026-11-20 the tree of D-118 was measured again: on ARM64 natively, at opt-level z, with the
default features and `hazmat`, the test of the dead stack for the lower opt-levels, compiled
without the feature, found the output of HKDF-SHA-256 and of HKDF-SHA-512 after a derivation of
32 bytes and after one of 200 bytes. That is finding F3 in a default build: below opt-level 3 the
kernels of the keyed hashes pass arrays of key words through memory, and D-76 promises that such
arrays are wiped at those levels. Decision D-119 restores the zeros: at the opt-levels 1, 2, s and
z a MAC and a KDF in one call, the key setup of an incremental MAC or of a MAC key and the end of
an incremental MAC end with the 16 KiB of D-116 in every build, with the feature and without it.
The feature governs opt-level 3 alone; at opt-level 0 these calls write no such zeros. Compared at
opt-level 3 in one codegen unit, with the default features and `hazmat`, no function of the
library differs from the tree of D-118, on x86-64 and on ARM64. Neither the tree of D-118 nor that
of D-119 was released.

## After a keyed hash

HMAC, KMAC, HKDF, the MACs of BLAKE2 and BLAKE3 and BLAKE3-KDF, in the default build:

- They wipe the buffers that they name, as D-76 requires. Secret outputs are `SecretBytes`, and a
  `Mac` and a `MacKey` wipe their keyed state when dropped.
- At the opt-levels 1, 2, s and z, a MAC and a KDF in one call, the key setup of an incremental
  MAC or of a MAC key and the end of an incremental MAC end with 16 KiB of zeros over the stack
  under them.
- At opt-level 3 they write no zeros over the stack frames of their calls. What the compiler saved
  of a key or of a keyed state in such a frame stays until later calls write over it. In the
  builds that D-117 searched without zeros, this was the list of the keyed hashes at opt-level 3
  above, and an incremental MAC left its keyed state in frames of the library. A build setting
  outside those builds can leave more. Their machine code in one call at opt-level 3 is that of
  the tree before D-116.
- At opt-level 0 they write no such zeros either.

With `stack-zeros`, the same calls end with zeros over the stack under them at opt-level 3 too,
with the sizes that D-118 gives. In every setting, the copy of a `Mac` or a `MacKey` that a return
or a move leaves in the caller's own frame is not wiped.

The operations of ML-KEM, ML-DSA, FrodoKEM and SLH-DSA on secret values end with zeros in every
build, and those that end an SLH-DSA signature cover the HMAC of PRF_msg inside it.

## What was verified

- `rust/tests/stack.rs` paints the stack, runs key generation, encapsulation, decapsulation and
  signing of ML-KEM, ML-DSA, FrodoKEM and SLH-DSA and the keyed hashes and KDFs, searches for
  their secrets and checks that the zeros lie where each call went deepest. On the tree before the
  fixes it fails. CI runs it in the release build, in the test profile and at opt-level z, and on
  the runners with AVX-512VL in the release build and the test profile. At opt-level 3 it runs the
  keyed hashes with `stack-zeros`. At opt-level z it runs with the default features and `hazmat`
  and with every feature, and there it covers a MAC and a KDF in one call only: the key setup and
  the end of an incremental MAC below opt-level 3 rest on the sweep below.
- The sweep of the lower opt-levels, on the binaries of 530eeff (the tree of D-117, whose zeros
  below opt-level 3 are those that D-119 keeps, and whose post-quantum code is that of `main`):
  opt-levels 2, s, z and 1; x86-64 as EPYC-Milan, Haswell with model 8Fh and qemu64, ARM64
  natively and as Cortex-A72; 28,000 jobs, none in error. The MACs ran in one call and in their
  incremental forms. The search found a value under the caller's frame in the control rows only,
  and no keyed-hash call read beyond its 16 KiB of zeros. The calls that went deeper than their
  zeros are ML-KEM encapsulation and decapsulation, at their 2,048 bytes, over the zeros of K-PKE
  under them; the search found nothing there.
- The same sweep at opt-level 3, over the s sets of SLH-DSA, HSS/LMS, XMSS and XMSS^MT, in the
  release build and with debug assertions: no value under the caller's frame. 126 jobs ended in
  a panic of the harness itself, each a later key generation of a stateful scheme in the same
  process.
- The search of D-116 over ML-KEM, ML-DSA, FrodoKEM, SLH-DSA, LMS and XMSS in 23 builds found none
  of their secrets after the fixes, where it had found values in 92 rows before them.
- With `stack-zeros`, the search over the keyed hashes found no value under the caller's frame in
  the 24 builds of D-117, 1,440 rows, and in the builds for x86-64-v3 with one codegen unit and
  with fat LTO, 10,760 runs of the grids of HMAC, KMAC and HKDF and 2,720 rows of the other keyed
  operations.
- The same probe and search over ML-KEM, ML-DSA, FrodoKEM and SLH-DSA in eleven builds, 4,854 rows,
  found no secret under the caller's frame.
- Under Windows, natively on the Zen 3, in the release build, with debug assertions and with fat
  LTO: 1,025,622 rows, in which every frame of the library lay within the zeros of that target.
  The test suite passed there: 167 tests with the default features, 306 with every feature.
- The CI of each pull request passed, 57 of 57 checks, before its merge.

## Released versions

The releases 1.0.0 and 1.0.1 predate the audit. The search of the dead stack was run on the tag
`rust-v1.0.1` with the audit's harness; 1.0.0 was not measured. In the builds that were run, 1.0.1
leaves:

- **F9.** FrodoKEM at opt-level 3: the whole shared secret after encapsulation and decapsulation,
  on x86-64 as EPYC-Milan and Haswell, built for x86-64-v3, in the portable build on both
  architectures, and on ARM64 natively in the default build.
- **F4.** ML-KEM at opt-level 3: the shared secret and the coins after encapsulation, the coins
  after decapsulation, and on x86-64 sigma after key generation, in the default builds on x86-64
  and ARM64, the portable builds, the build for x86-64-v3 and ARM64 with fat LTO. The search did
  not find rho', K or the states of H(xi) of ML-DSA.
- **KMAC256** at opt-level 3: its state after the key, 200 of 200 bytes on ARM64 and 160 on
  x86-64, and on x86-64 96 of the 136 bytes of its final state.
- **F3.** At opt-levels z and s, on both architectures: HMAC its key XORed with the pads and its
  key states, HKDF its PRK, its input keying material and its output, by build.
- **Keyed hashes at opt-level 3** in one call, as listed above for c48e64f: the outer state of
  HMAC-SHA-512, the BLAKE2b state after the key and, for an empty message, the key, the key of a
  keyed BLAKE3 of 16 KiB, and output or input bytes of HKDF and BLAKE3-KDF, by build. N1: an
  incremental MAC leaves its keyed state.

The search did not find the PRF_msg state of SLH-DSA in the builds run; opt-level 1, and the
SHA-2 sets of 192 and 256 bits with fat LTO on ARM64, were not run. F1 is in neither release: the
source of both tags has no `drop(lanes)`, and the search of 1.0.1 found no FORS secret value.

Not measured: 1.0.0 itself; the opt-levels 0, 1 and 2; one codegen unit; fat LTO on x86-64;
debug assertions; other processor models; Windows; LMS and XMSS. Between the two tags the code of
ML-KEM and ML-DSA changed in visibility only, and that of HMAC, HKDF, KMAC, BLAKE2, SLH-DSA and
the MACs did not change; FrodoKEM, BLAKE3 and the CPU dispatch changed.

The 1.0.x line receives no patch. 2.0.0 holds the fixes of this record. Version 2.0 removes the
WebAssembly and 32-bit targets ([D-105](../spec/decisions.md#decision-d-105)), so their users stay
on 1.0.x, which keeps these residues.

## What is not covered

- The AVX-512 kernels were not executed under emulation; the stack test runs them on the CI
  runners that have AVX-512VL, and the frames of the 512-bit BLAKE3 tree were read from the code
  only.
- Build settings, compiler versions and processors outside the lists of D-115 to D-119 and of the
  sweeps above.
- BLAKE3-KDF with more than a chunk of input keying material; the parameter sets of FrodoKEM and
  SLH-DSA that were not run; a second key generation of HSS/LMS and XMSS in one process.
- For one parameter set of ML-KEM, ML-DSA and FrodoKEM the search looks for the noise seeds and
  the first polynomial of the secret vectors; it does not look for the other polynomials or for
  the round variables of SHA-2 and Keccak.
- Under Windows: one processor only, not the MSVC target, UEFI or Windows on ARM64; the frames of
  the allocator are not counted; `rust/tests/stack.rs` does not run under Windows.
- The constant-time check of CI (`rust/tests/ct.rs` under valgrind) runs 2 of the 12 SLH-DSA sets
  and LMS over SHA-256 with n = 24 only; its build leaves out SHA-NI and AVX-512 on x86-64 and the
  SHA-3, SHA-512 and DIT paths on ARM64, and runs at the release opt-level only.
- `rust/src/ct.rs` uses `core::hint::black_box` in `difference` and `select`, for which the Rust
  documentation gives no guarantee; the audit noted this as an open question and did not resolve
  it.
- The robustness tests are mutation-based, not coverage-guided.
- No experiment on physical side channels or fault injection was made, and no formal
  verification was done.
